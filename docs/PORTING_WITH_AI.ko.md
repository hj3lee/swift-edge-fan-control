# 호환되지 않는 노트북에서 AI와 함께 직접 조사·제작하기

이 문서는 다른 기기에 SFE16-43 레지스터를 복사하는 안내가 아닙니다. **읽기 관찰 → 공식 인터페이스 검증 → 펌웨어 분석 → 제한된 실제 시험 → 복귀 검증 → 앱 구현**이라는 제작 과정을 재현하기 위한 워크플로우입니다.

## 1. 장비와 현재 상태를 먼저 기록

관리자 PowerShell에서 아래처럼 CIM으로 모델, 보드, BIOS를 읽습니다. 처음에는 쓰기 작업을 하지 않습니다. 공유할 때 일련번호, UUID, 사용자 이름 등 식별자는 제거합니다.

```powershell
Get-CimInstance Win32_ComputerSystem | Select-Object Manufacturer, Model
Get-CimInstance Win32_BaseBoard | Select-Object Manufacturer, Product
Get-CimInstance Win32_BIOS | Select-Object SMBIOSBIOSVersion, EmbeddedControllerMajorVersion, EmbeddedControllerMinorVersion
Get-CimClass -Namespace root/wmi | Where-Object CimClassName -Match 'Acer|Fan|Thermal'
```

AC/배터리, 온도, 양쪽 팬 RPM, OEM 프로필과 관련 서비스도 기록합니다. SMBIOS 숫자 필드가 실제 문자열 EC 버전을 의미한다고 가정하지 않습니다. 이 프로젝트의 초기 모델명 검사 버그처럼 `Swift SFE16-43`와 짧은 판매 모델명의 차이도 확인합니다.

## 2. 공식 WMI·OEM 경로를 먼저 시험

클래스와 메서드 시그니처를 실제 장비에서 조회하고 OEM 앱의 호출을 조사합니다. 인터넷 앱이 다른 Acer 모델에서 쓰는 인코딩을 이 기기에 그대로 적용하지 않습니다. 각 호출 전후에 **실제 RPM, 모드 및 단계 읽기, 온도**를 기록합니다. `ReturnValue=True` 또는 `gmOutput=1`만으로 성공이라고 판정하지 않습니다.

SFE16-43에서는 이런 반환값이 있어도 팬 RPM은 바뀌지 않았습니다. 구버전 SMM 코드에서 지원하지 않는 하위 함수가 비슷한 반환값으로 바뀌는 경로를 찾았습니다. 현재 펌웨어와 동일하다는 증거는 아니지만 반환값만 믿으면 안 된다는 단서였습니다.

## 3. 공식 펌웨어를 실행 없이 분석

정확한 모델과 버전의 제조사 패키지를 확보하고 출처·SHA-256을 기록합니다. 플래셔는 실행하지 않습니다. ACPI DSDT/SSDT의 EC 영역, WMI GUID, SMM 호출 경로를 살펴보고 UEFIExtract/압축 해제 도구로 관련 모듈을 추출합니다. EC 프로세서 종류와 주소 매핑을 확인한 다음 디스어셈블합니다.

이 프로젝트에서는 BIOS 1.63 패키지의 8051 EC 코드에서 자동 단계 선택 분기, 수동 제어 비트, 팬 단계, 센서 값과 내부 목표 테이블을 추적했습니다. 설치된 V1.71을 같은 코드라고 간주하지 않고 현재 장비에서 별도 짧은 시험을 수행했습니다. 확보하지 못한 버전은 모른다고 남깁니다.

## 4. 읽기로 주소의 의미부터 검증

문서·코드 근거가 있는 읽기 경로만 사용합니다. 기존 OEM/RPM 측정과 비교하고 바이트 순서, 값의 범위, 갱신 주기를 확인합니다. RPM을 나타내는 주소에 값을 쓰면 목표 RPM이 설정될 것이라고 가정하지 않습니다. 임의 EC 주소 스캔·무차별 쓰기, 무작정 서비스 종료, 드라이버 보안 해제는 워크플로우에 포함하지 않습니다.

## 5. 첫 쓰기 전에 복귀 수단 만들기

변경하려는 비트만 바꾸고 다른 비트는 보존합니다. 원래 상태를 저장하고, 센서 실패·고온·프로세스 종료 시 제조사 자동으로 복귀하는 독립 워치독을 먼저 만듭니다. 온도 기준은 실제 기기 사양과 조건에 맞게 정합니다. 이 저장소의 90°C를 다른 기기의 검증된 기준으로 인용하지 않습니다.

센서 실패·가짜 고온·프로세스 비정상 종료를 주입해 복귀를 검증합니다. 워치독이 같은 드라이버 오류를 공유한다는 한계도 남깁니다. 사용자와 기기별 실험 범위를 정하고, 확인되지 않은 팬 정지 단계나 펌웨어 플래시는 별도 문제로 취급합니다.

## 6. 짧은 실제 시험을 단계적으로 늘리기

첫 시험은 근거가 있는 한 단계만 짧게 바꿉니다. 읽기 반영, 실제 RPM 반응, 온도와 자동 복귀를 확인한 뒤 두 팬·다른 단계·긴 유지로 늘립니다. 외부 덮어쓰기와 통신 타임아웃을 서로 구분합니다. 실패를 숨기거나 자동으로 계속 덮어쓰지 않습니다.

통신 품질은 **읽기 시도 수/타임아웃 수, 분당 오류, 성공 센서 간 최대 시간, 재시도 회복, 최종 중단**을 함께 기록합니다. 폴링을 줄여 분당 오류가 감소했다고 호출당 품질도 개선됐다고 주장하지 않습니다. 캐시된 RPM을 새 측정값으로 세지 않습니다.

## 7. 하드웨어 프로필과 앱 분리

모델·보드·BIOS별 허용 목록과 주소·인코딩을 프로필로 정의합니다. 증거가 부족한 장비는 차단합니다. 정책 엔진은 하드웨어 없는 테스트로 히스테리시스, 감속 지연, 고온 우선, 오류 복귀를 검사합니다. 시작 프로그램, 절전, 종료, 로그 회전은 따로 검증합니다. 조사 결과와 미확인 항목을 README에 모두 씁니다.

## AI에게 보낼 프롬프트 예시

```text
내 노트북의 팬 제어를 조사하고 Windows 앱을 만들고 싶다.
모델/보드/BIOS: [CIM으로 읽은 정확한 값]
공식 펌웨어 링크와 파일 해시: [확인한 정보 또는 미확보]
현재 온도/RPM/OEM 프로필: [실측]

먼저 읽기 전용 CIM/WMI 조사로 기기 상태와 가능한 공식 경로를 확인하라.
다른 모델의 레지스터를 추정해 쓰지 말고, 메서드 반환값만으로 성공 판정하지 마라.
필요하면 공식 펌웨어를 실행 없이 분석하고 버전 차이를 명시하라.
쓰기에 앞서 독립 워치독과 자동 복귀를 구현하고 오류 주입으로 검증하라.
근거가 확보된 단계만 짧게 시험한 뒤 실제 RPM/온도/복귀 로그로 판단하라.
고정 팬 단계와 임의 RPM 제어를 구분하라.
호환성, 장시간 안정성, 배터리 영향은 각각 검증 범위대로만 주장하라.
UI는 고정 단계, 온도 커브, 히스테리시스, 로그인 실행, 로그를 제공하라.
결과물에 소스·빌드 절차·실측 기록·미해결 문제를 포함하라.
```

AI가 주소를 제안했다는 사실은 검증 근거가 아닙니다. 최종 판단 근거는 해당 모델·버전의 코드 또는 문서와, 제한된 실제 시험의 읽기·RPM·온도·복귀 기록입니다.
